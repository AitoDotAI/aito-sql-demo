Four rows do not yield a confident 90%. Support-tempering — on by default — shrinks the answer back toward the base rate, and the calibration / support-tempering(auto) factor in $why reports exactly how much it shrank. Measured in-repo, not asserted: on redundant weak features a plain naive Bayes collapses to ~0.60 accuracy while Aito holds 0.920 at identical calibration (books/test/cases/ReexpVsAitoInferenceTest). So there is no minimum-n rule and no refusal to answer: every slice is explorable because every slice is answered honestly.

Design notes. One component, four panels, parameterised by (object, filter context) — every link opens another instance of the same screen, which is why "endlessly navigable" costs almost no code. The trail and the context chips are the same thing the SQL is: an accumulating WHERE.
No minimum-n, no greyed-out cells, no refusals — the engine tempers, so unrestricted filtering is a feature to demonstrate, not a risk to guard against.
Lift never relies on colour alone (▲/▼ glyph plus the number) since red↔green separate at only ΔE 2.7 under deuteranopia. Teal #12B5AD is used for rules and fills only; teal text is the darkened #0b6f6a at 6.01:1.
Two panels depend on filed tickets: the text panel needs analysed-text DDL (td-20260816165937059483), the header arithmetic needs why => true (td-20260816220020308261).
